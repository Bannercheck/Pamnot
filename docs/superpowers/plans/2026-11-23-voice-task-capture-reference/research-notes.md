########## speech
RECOMMENDATION: For v1, use the speech_to_text plugin (csdcorp) behind a small Dart `VoiceRecognizer` interface, and leave a native Swift DictationTranscriber backend as a possible phase 2. Version choice: stable 7.5.0 (published 2026-09-14), or pin exactly 7.6.0-beta.4 (2026-09-25), which fixes an onDevice bug and adds `hasOnDeviceSupport`. Both declare sdk ^3.12.0 and flutter >=3.44.0. Both resolved cleanly against Pamnot's real pubspec under Flutter 3.47.8 / Dart 3.13.7 (`flutter pub get` in /tmp/claude-0/-home-user/8bed75ce-f409-56cc-a847-c9a160392e81/scratchpad/pubcheck). The plugin uses only SFSpeechRecognizer on iOS and macOS. I read the Swift source of both versions: no SpeechAnalyzer code. The maintainer replied "No schedule" on the SpeechAnalyzer issue (#611, July 2025). The plugin provides:
- partial results
- `pauseFor`/`listenFor` (Dart timers measured from the last change in the result) and `changePauseFor()`
- `locales()`/`systemLocale()`; on iOS, `systemLocale()` returns `Locale.preferredLanguages[0]`, i.e. the phone language
- `onDevice` (default false), and macOS support
- SPM packaging, which matches Pamnot's FlutterGeneratedPluginSwiftPackage setup

TURKISH, the deciding fact: tr-TR is supported by SFSpeechRecognizer on the server and on-device. Apple's WWDC19 on-device list includes Turkish, and Apple's feature page lists Turkish for On-Device Dictation. tr-TR is also supported by DictationTranscriber (iOS/macOS 26+). It is NOT supported by SpeechTranscriber, the new higher-quality model. Two independent 2026 reports agree: 8 of 21 languages on iOS 27.0 with no Turkish, and tr-TR listed as "dictation-only" on macOS 27.2. Apple's docs say DictationTranscriber "uses the same speech-to-text machine learning models as … SFSpeechRecognizer does when it is configured for on-device operation". So for a Turkish phone, a native SpeechAnalyzer plugin gives no accuracy gain over the plugin. Its real advantages are operational:
- no Siri/Dictation toggle requirement (SFSpeechRecognizer can fail with kLSRErrorDomain 201 "Siri or Dictation is disabled")
- apparently no separate speech-recognition permission prompt (Apple's iOS 27 sample asks only for the microphone)
- no server throttling
- volatile results with `frequentFinalization`, and a VAD module (SpeechDetector)

Those advantages do not outweigh the costs for this developer:
- No Mac, so the Swift code can't be run locally.
- The Simulator is unsupported.
- Every iteration means CI plus a sideloaded install.
- iOS 26+ only, so a fallback is still needed for iOS 16–25.
- Asset download through AssetInventory.
- Apple's convenience APIs (CaptureInputSequenceProvider, AnalyzerInputConverter) are iOS 27-only, which would need the xcode-27 runner. macos-latest is now macos-26 with Xcode 26.6.

Revisit native if field data shows error 201, server throttling, or slow first results.

TIMES AND DATES IN TRANSCRIPTS: Apple does not document how the recognizer formats numbers, and I found no captured Turkish transcripts. The evidence I did find:
- An English report: numbers of 10 and above come back as digits ("twenty"→"20") and below 10 as words ("six"). This is old (2017).
- Apple's own Turkish copy writes times as a digit plus a TYPOGRAPHIC apostrophe and suffix: "saat 7’de", "saat 08:00’e" (U+2019).
- Auto-punctuation is not offered for Turkish dictation.

So expect a mix: "saat 10’da" / "saat 10'da" / "saat onda" / "akşam 7’de" / "akşam yedide", plus English "6 PM", "6 p.m." or "6:30 PM". I ran the existing quickParse on these forms (/tmp/claude-0/-home-user/8bed75ce-f409-56cc-a847-c9a160392e81/scratchpad/qp/run.dart). It mishandles most of the non-ASCII and spoken-word variants, so a normalization step (or parser fixes) before quickParse is needed for voice input.

DESIGN NOTES FOR THE SHEET:
- Choose the locale from the phone language: preferredLanguages / PlatformDispatcher locales. Match exactly against `locales()`, then fall back by language code. An unsupported locale such as en-TR otherwise silently falls back to the dictation-keyboard language, or fails.
- Start with `pauseFor` = 6 s (idle close), and on the first non-empty partial call `changePauseFor(~1.5–1.8 s)` (end of utterance).
- Set `listenFor` to about 30 s.
- Use `onDevice: false`: iOS still works offline (reported in airplane mode), and it avoids the on-device "transcript resets after ~2 s pause" bug (#552).
- Leave `autoPunctuation` false.
- Strictly serialise listen/stop: open issue #680 is a crash when `listen()` overlaps a previous session or a late stop; this is exactly the re-arm loop.
- Start listening only once the app is resumed/foreground: the plugin uses a mixable session, and recording started from the background fails with `cannotStartRecording`.
- Cancel on lifecycle pause; the plugin does not observe audio interruptions.

On the user's idea of triggering from an accessibility tool: Voice Control is available in Turkish. But Voice Control keeps its own microphone pipeline, and there is a forum report of it interfering with Siri recognition. Test it on a device as a trigger before relying on it; Back Tap and the Action Button don't hold the microphone.

- Add speech_to_text for v1. Prefer pinning exactly `speech_to_text: 7.6.0-beta.4` for the onDevice fix and hasOnDeviceSupport. If you stay on ^7.5.0, never pass onDevice:true. Put it behind a small Dart interface (start(locale), partial/final stream, stop, cancel) so a native DictationTranscriber backend can replace it later without UI changes.
- Locale = phone language. Read PlatformDispatcher.instance.locales (or the plugin's systemLocale()), normalise '_'/'-', then pick:
- an exact match in `await speech.locales()`,
- else the first entry with the same languageCode (en-TR becomes en-US/en-GB, tr becomes tr-TR),
- else en-US.
Pass the result as localeId explicitly. Don't rely on SFSpeechRecognizer's silent fallback to the keyboard dictation language.
- Listen options: SpeechListenOptions(partialResults: true, onDevice: false, autoPunctuation: false, cancelOnError: false, listenMode: default/confirmation). Avoid ListenMode.dictation, because the .dictation hint has been tied to error 201 when the Dictation toggle is off. onDevice:false lets iOS use the server when online (best accuracy for tr-TR), still works offline, and avoids the on-device pause-reset bug (#552).
- Silence handling with one session per task:
- listen with pauseFor = 6 s (idle → close the sheet) and listenFor ≈ 30 s (safety cap, well under the 1-minute server limit);
- on the first non-empty partial, call changePauseFor(≈1.6 s) to detect end of utterance;
- on status done/notListening, take the final words, parse, show the preview for 2 s, save, and only then call listen() again.

## RISKS
- The re-arm loop (stop, then listen again) is exactly the pattern behind open crash issue #680 (EXC_BAD_ACCESS in AVAudioIONodeImpl). If calls aren't strictly serialised, expect intermittent crashes.
- speech_to_text has a single main maintainer and SFSpeechRecognizer only. If Apple deprecates SFSpeechRecognizer or degrades it further (as with iOS 17's Siri/Dictation dependency), Pamnot depends on that maintainer or on writing the native backend.
- Error 201 'Siri or Dictation is disabled' cannot be detected in advance (isAvailable lies). Users who turned off Dictation get a failing sheet unless the app explains the fix.
- Server recognition (onDevice:false) sends audio to Apple and is subject to undisclosed per-device and per-app daily limits. A heavy user could hit throttling. On-device recognition avoids the limits but brings the #552 pause-reset bug and the #654 first-listen error.
- Recognizer output format for Turkish times is undocumented and may change between iOS versions. Without normalisation, the current quickParse mis-parses typographic apostrophes, akşam/PM, number words and English 'p.m.'/'6:30 PM' (verified by running it).
- The native SpeechAnalyzer path can't be compiled or debugged locally (no Mac, Simulator unsupported). Its first use may need an asset download, and its convenience APIs need iOS/Xcode 27. Doing it in v1 would likely cost far more iteration time than it saves.
- macOS: Pamnot's sandbox entitlements lack audio-input today, so the mic is silently unavailable until it is added. The plugin README also warns that permission requests crash when the app is launched from VS Code.
- Voice Control as a trigger may compete for the microphone or interfere with recognition (one forum report on iPadOS 26.7.2). This is unverified for third-party apps.

########## intents
Verdict: App Intents fit this project as it is. Put two Swift files straight into the Runner target. VoiceTaskIntent.swift holds the AppIntent (openAppWhenRun = true) and an AppShortcutsProvider. PamnotLaunchBridge.swift is a small in-app plugin. In didInitializeImplicitFlutterEngine, register the bridge through `engineBridge.pluginRegistry.registrar(forPlugin: "PamnotLaunchBridge")`, not only `applicationRegistrar.messenger()`. A plugin registrar can also call `addSceneDelegate`, and that is needed to catch pamnot://ses on cold and warm start. The intent's perform() calls the bridge directly and does not open pamnot://ses. The bridge keeps one pending action, and Dart pulls it with `takePendingAction` after installing its handler. Native also sends `actionAvailable` on warm start, and the engine's channel buffer holds that message if Dart is not ready yet. Whichever side runs first, the event is delivered once and never lost. I read the engine source in the 3.47.8 SDK: FlutterViewController triggers the implicit-engine callback before the scene's willConnect is passed to plugins, and the scene-delegate array is weak, so the bridge must be a singleton. Free Apple ID: App Intents and App Shortcuts need no entitlement. The Siri capability, which is paid-only in Apple's table, applies only to SiriKit Intents extensions.

URL scheme: registering `pamnot` (CFBundleURLTypes) does not change home_widget. Widget URLs reach the containing app whether or not the scheme is registered. home_widget's scene delegate claims only URLs with a `homeWidget` query item and returns YES, so Flutter never routes them. The real pitfall is FlutterDeepLinkingEnabled, which defaults to true since Flutter 3.27. Pamnot uses MaterialApp(home:), so an unclaimed pamnot://ses becomes `pushNamed('/')` and pushes a second HomeShell. pamnot://x?y=1 becomes '/?y=1', which has no route and throws. On cold start the engine then hands the URL back to iOS. Fix: set FlutterDeepLinkingEnabled = false, make the bridge claim only the hosts ses/voice, and never auto-save task text that arrives in a URL.

Phrases and the 16.0 target: the AppShortcut initializer that takes shortTitle and systemImageName requires iOS 17. Putting `if #available` inside appShortcuts is reported to crash or break phrase extraction, and AppShortcuts.xcstrings is rejected below iOS 17. With 16.0, the least fragile setup is the iOS 16 `AppShortcut(intent:phrases:)` plus AppShortcuts.strings in en.lproj/tr.lproj, translated 1:1 per source phrase. Every phrase must contain \(.applicationName). In Turkish, keep the name bare with no suffix ("Pamnot ile görev ekle", not "Pamnot'ta …"). I read the parser files in the checkout and ran the 145 proposed test cases. The current parser, `quickParse`, gets 31 of them right; a throwaway reference parser in the scratchpad (406 lines, `dart analyze` clean) gets all 145. That shows the expected values agree with each other and can be implemented. The current parser was built for typed input: digit times plus a few day words and weekdays.

**What `quickParse` handles today** (`/home/user/wt/main/lib/core/quick_parse.dart`)
- **Times.** Four patterns, tried in this order:
  1. `(saat |at )?H[:.]MM` with an optional `'de/da/te/ta`
  2. `saat H` with an optional `'de/da/te/ta`
  3. `H am/pm`
  4. `at H`
- **Hours are read literally as 24-hour.** "saat 3" means 03:00.
- **Day words.** Only the first match counts: öbür gün / yarından sonra / day after tomorrow = +2; bugün / today / tonight / bu akşam = today, with no time; yarın / tomorrow = +1; haftaya / gelecek hafta / next week = +7.
- **Weekdays.** Turkish and English, only when no day word matched. Optional `günü|ya|ye|a|e`. Gives the next occurrence; the same weekday gives +7.
- **Time with no day.** Goes to today. If that time has passed and the text has no bugün/today, it moves to tomorrow.
- **Title.** Whatever text is left, with spaces collapsed and the first letter capitalized the Turkish way.
- **Not handled:** spoken number words, buçuk / çeyrek / geçe / kala, part-of-day words, relative offsets ("2 gün sonra", "in 2 hours"), absolute dates ("15 Aralık", "15'inde", "on the 15th"), weekend and end of month, this/next + weekday, filler and reminder phrases, typographic apostrophes, and dictation punctuation.

**Bugs in the current typed parser that also hurt dictation** (all confirmed by running it)
- "Pay rent at 6:30 PM" gives tomorrow 06:30 with the title "Pay rent PM". Apple's English dictation writes times as "6:30 PM", so this case matters.
- "Call mom tomorrow at 6 PM." gives the title "Call mom at .".
- "saat 3'te" gives 03:00 tomorrow.
- "Yarın saat 10’da" (curly apostrophe) gives the title "’da toplantı".

**Rule for a bare hour like "3'te"** (no sabah/akşam, no am/pm)
- Hours 0, 13–23 and leading-zero forms ("08.30") are taken literally.
- Otherwise 1–6 means afternoon (13–18), 7–11 means morning, and 12 means noon.
- **When no day is named:** if that time has already passed today, 7, 8 or 9 move to 19, 20 or 21 if that is still ahead; any other hour moves to tomorrow.
- **When a day is named** ("yarın 7'de"): the base value is used with no flip.

Why this rule:
- Everyday Turkish uses the 12-hour clock and relies on words like sabah and akşam.
- Apple's own Turkish Siri example "Bugün saat 3'e bir toplantı yarat" only makes sense as 15:00.
- Todoist puts a time with no date on today unless it has passed, then tomorrow.
- The listening sheet's ~2 s preview with "Düzelt" lets the user correct the rare wrong guess.

- Leave `quickParse` and its 7 tests exactly as they are, so typed quick-add does not change.
- Add a speech pipeline in two parts:
  1. `normalizeSpoken(text, lang)` does text-only work that does not depend on the clock: unify apostrophes, strip punctuation, strip filler and reminder phrases (and set a reminder flag), turn number words into digits only where they clearly mean a time or date, and rewrite buçuk / çeyrek / geçe / kala / yarım to "h.mm".
  2. A new extractor that depends on `now` handles part of day, the bare-hour rule, relative and absolute dates, weekends and month ends. It returns title, due, hasTime, remind, an ambiguity flag and the matched spans.
- A normalizer alone placed in front of `quickParse` is not enough. `quickParse` cannot express "+2 days", absolute dates or part of day. Its order-sensitive patterns also leave "at" and "PM" in titles, and fixing that in place would change typed results.

## RISKS
- The real tr-TR output of SFSpeechRecognizer and DictationTranscriber for spoken times is undocumented. It may write '10.30'da', '10:30'da', '10’da', 'onda', '10 30' or '10'30'. The normalizer covers the first four, but untested shapes can slip through until transcripts from a real device are collected.
- False positives with standalone part-of-day words: the reference parser reads 'sabah kahvesi iç' as tomorrow 09:00, because 'kahvesi' is not in the compound-noun stop-list. Any list of compound nouns will be incomplete.
- English 'at N' followed by a noun is read as a time: 'look at 3 options' gives 15:00 with the title 'Look options'.
- Time ranges are not handled: 'yarın 10'dan 12'ye toplantı' gives 12:00 with '10'dan' left in the title. A range rule (take the start time) is needed.
- An apostrophe before a weekday suffix ('pazartesi'ye kadar') leaves '’ye' in the title in both parsers. 'haftaya bugün' (a week from today) and 'gelecek ay' (next month) are not handled.
- Turning the verbal noun back into an imperative ('aramayı' → 'ara') is a suffix heuristic and can damage titles whose last word only looks like -mAyI/-mAmI.
- The bare-hour guess can surprise users (e.g. '9'da' said at 09:05 becomes 21:00; '10'da' said at 14:00 becomes tomorrow). The 2-second preview and 'Düzelt' are the safety net, but a wrong reminder is possible if the user does not look.
- 'in 2 hours' is added as an exact Duration while 'N gün sonra' uses calendar days. Across a DST change these behave differently. Turkey has no DST, but English users may. Tests that depend on DST are tied to the machine's time zone and were not written.
- Parsing live partial results can make the preview flicker as words arrive (e.g. 'saat 3' then 'saat 3 buçukta'). Save only from the final result.
- The reference implementation is a throwaway built only to check the cases; it is not production code. It does not record matched spans, and its regex order matters. It should be re-implemented test-first, not copied as is.

########## integration
How the voice-capture feature plugs into the Pamnot app (main checkout /home/user/wt/main, read-only; all trials ran in a scratch copy).

1) Quick-add and reminders. Quick-add is `QuickAddField` (lib/ui/tasks/task_editor.dart:295-356). It sits on the Today page (today_page.dart:45) and the Track page (track_page.dart:66). Its `_submit` calls `AppController.addQuickTask` (app_controller.dart:438-445), which does `quickParse(text, now())`, then `draftTask(due: r.due, hasTime: r.hasTime).copyWith(title: r.title)` and `upsertTask`. It never sets `remindAt`. Only tasks with `remindAt` become alerts: `alerts()` (321-330) emits `Alert(key: 't:${t.id}', …, at: t.remindAt!)`. A change to tasks, reminders or settings starts an 800 ms debounced `syncAlerts()` (291-296). That calls `LocalNotificationScheduler.sync`, which cancels all pending notifications and schedules the 60 soonest. The notification id is FNV-1a of the key `t:<taskId>` / `r:<id>`, and the payload is the key. Result: a spoken "yarın 10:00 toplantı" gets a date and time but no notification. Two changes are needed:
- an explicit remind option on the quick-add path;
- a notification-permission request. Today only the task/reminder editors and Settings ask, and the init flags are all `false`. The request should happen while the mic is off.
A scratch test confirmed `remindAt == null` and that no `t:` alert is created.

2) External triggers. `notificationTaps` (home_shell.dart:16) is a single-slot `ValueNotifier<String?>`. It is fed by:
- the notification `onTap` (main.dart:20);
- `getNotificationAppLaunchDetails` on cold start (reminder_scheduler.dart:124-127);
- HomeWidget (main.dart:21; widget_sync_io.dart:16-23, host `today`).
HomeShell listens and also checks once after the first frame (34-39), so a value set before the first frame is not lost. That pattern is the one to reuse. Two cautions: `_onNotification` sends every prefix other than `w:` and `t:` to the Reminders tab (line 50), and the single slot can be overwritten.

For `pamnot://ses` on iOS:
- `ios/Runner/Info.plist` has no `CFBundleURLTypes`, so iOS will not route the scheme to the app.
- It also lacks `FlutterDeepLinkingEnabled`, and Flutter has turned deep linking on by default since 3.27 (Android turns it off in its manifest).
- In a scratch widget test, sending `pushRouteInformation('pamnot://ses')` to the current app pushed a second HomeShell onto the Navigator.
- Overriding `didPushRouteInformation` in `_PamnotAppState` fixes this. That state is already a `WidgetsBindingObserver` and is registered before MaterialApp's, so it sees every `pamnot://` URL first and returns true. The prototype passed the whole suite (49 tests).

For the App Intent (Action Button, Back Tap, Voice Control, Spotlight, Siri), the most reliable hook is a pull model, so the request survives cold and warm start:
- Swift stores a pending "voice" flag.
- Dart reads and clears it through a method channel. Create the channel in `didInitializeImplicitFlutterEngine` with `engineBridge.applicationRegistrar.messenger()`.
- Dart pulls after `runApp`, after the first frame, and on every `AppLifecycleListener.onResume`.
- Dart then raises one dedicated voice-request flag. HomeShell consumes it like `notificationTaps` and pushes a full-screen route, with an "already open" guard.
Whatever accessibility tool the user binds (the user's point: step 1 can sit behind a more reliable accessibility tool), it ends in this same hook.

## RISKS
- Wrong recognition language: if no localeId is passed, speech_to_text uses Locale.current. The app declares no CFBundleLocalizations, so a Turkish phone may get an English recognizer (medium confidence; verify on device).
- Silent missing reminders: addQuickTask leaves remindAt null today. Even with remindAt set, syncAlerts runs on an 800 ms debounce timer, so if the user locks the phone right after saving, the notification may not be scheduled until the app next resumes.
- A permission prompt during listening (speech, mic or notifications) makes the app inactive and kills the recognition task. The sheet must not treat that as a user interruption, and must not ask for notifications mid-listen.
- Duplicate HomeShell: with iOS deep linking on by default, any pamnot:// URL that is not intercepted pushes a second HomeShell. Reproduced in a scratch widget test.
- CI blind spots:
- the iOS job does not run on PRs or on branches without '[full-build]';
- Swift files not in project.pbxproj are silently skipped;
- missing NSSpeechRecognitionUsageDescription or NSMicrophoneUsageDescription compiles fine but crashes at runtime;
- `flutter analyze` ignores ios/**.
- VoiceOver output or the app's own start/stop sounds could be captured by the mic and transcribed into tasks, because the session is playAndRecord + defaultToSpeaker + mixWithOthers. Needs a device test with VoiceOver.
- Voice Control used as the trigger (custom command) also listens to the mic. It may compete with SFSpeechRecognizer or interpret the dictated task as commands. Needs a device test; Back Tap or the Action Button may be the more reliable accessibility trigger.
- Apple speech limits: per-device daily limits, network dependence for some locales, and a 1-minute cap per task. A long re-arm loop can hit throttling and must degrade to an 'unavailable' state with retry.
- Spoken Turkish times often come out as "10'da", "akşam 7'de" and similar, which quickParse does not parse or parses wrongly (e.g. 'bu akşam saat 7' becomes 07:00 tomorrow). That leads to tasks without times or with wrong reminders.
- The shared `notificationTaps` single slot can be overwritten if a voice trigger and a notification tap arrive together, and an unknown prefix navigates to the Reminders tab.
- Privacy: pamnot://ses lets any app or website open Pamnot straight into listening. The mic must only arm after the user has granted permission. Never accept task text or parameters from the URL. This also falls under the repo's security-audit rule.
- Pending timers in the sheet (gap, preview, idle) will make widget tests fail with 'A Timer is still pending' unless they are cancelled on dispose and the tests pump past them.
